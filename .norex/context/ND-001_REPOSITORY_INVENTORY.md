# ND-001 — Repository / Current-State Inventory

Status: evidence-backed inventory captured during Shadow Foundation. No existing application files were modified.

## Repository shape
- Static-generated web application: source under `web/`, generated by `scripts/build.mjs`.
- EA/club archive: versioned JSON under `data/`, refreshed by automation.
- Backend/API/bot: Cloudflare Worker under `bot/`.
- Cloudflare persistence/services: D1, KV, R2, Workers AI, and SQLite-backed Durable Objects.
- Discord is a first-class integration and identity/community surface.
- Deployment/automation uses GitHub Actions; public site configuration points to GitHub Pages.

## Runtime/data flow
EA Pro Clubs/data sources -> fetch/build scripts -> committed data archive -> generated static website.
Browser/member surfaces <-> Cloudflare Worker/API <-> D1/KV/R2/Durable Objects/Workers AI <-> Discord/external integrations.

## Tests / deterministic validation
- `tests/run.mjs` performs syntax checks, site build, and parallel feature tests.
- 54 feature test modules are present.
- GitHub Actions test workflow runs on pushes to main (excluding data-only changes), pull requests, and manual dispatch.
- This existing deterministic runner should be reused by Norex Dev rather than replaced without evidence of need.

## Backup/recovery
Nightly workflow exports D1, compresses it, and stores it in R2 with a restore runbook.
Known gap documented by the repository: R2 media itself is not backed up. Loss of the media bucket can lose feed media/avatar/report artifacts.
EA data archive is separately recoverable through Git history.

## Design-system evidence
The visual system is distributed, not a single stylesheet:
- `web/style.css` contains foundational brand tokens and broad shared styling.
- feature-specific CSS/JS modules contain additional components and responsive behavior.
- a shared member UI kit exists in Git history.
ND-003 must extract tokens -> primitives -> components -> feature styles -> responsive behavior from actual repository evidence.

## Git/history characteristics
Automated EA-data updates create commits approximately every 10 minutes and dominate normal Git history.
Norex Intelligence should classify/suppress DATA_AUTOMATION commits from normal engineering context while retaining them when data-history questions require them.
Suggested classes: ENGINEERING, FEATURE, FIX, QA, DOCS, INFRA, DATA_AUTOMATION.

## Branch state observed during inventory
The Shadow Foundation branch and main are diverged because main continues receiving automated data commits while foundation work proceeds. This is expected in Phase I.
Synchronize main -> foundation when needed; do not merge foundation into main until adoption is approved.

## Verified constraints / risks
1. Do not infer roadmap completion from feature existence alone; exposure and QA state may differ.
2. Owner-only features require explicit validation before broader rollout.
3. R2 media backup is an acknowledged recovery gap.
4. High-frequency data commits create context noise and branch churn.
5. Design authority must be extracted from current implementation rather than recreated.
6. Existing CI/test infrastructure is substantial and should be integrated, not duplicated.
7. Norex United runtime must remain independent from Norex Dev OS during and after foundation work.

## ND-001 conclusion
The repository is not an early prototype. It is a substantial member-facing platform with a static-generated frontend, Cloudflare-backed application services, Discord integration, extensive D1 schema evolution, feature gating, and deterministic tests.

FE and BE statuses in the Master Roadmap must be reconciled from this implementation/history evidence during ND-002 rather than initialized as new work.
